# Event copy, cover artwork, and social draft generation

Status: Accepted decisions consolidated on 2026-10-23.
Slack channel-list refinement accepted and implemented on 2026-10-27.

Scope: editorial formats, business ownership, generation ports, durable proposals,
and organizer review. Configuration, supported actions, and recovery live in the
[content integration guide](../integrations/content.md).

## Context

Generated copy and illustrations save preparation time but cannot establish event
facts or grant publication authority. Human submissions need the same review and
traceability. Grouping every editorial rule under a generic content component
would also couple unrelated event, publication, and communication policies to a
provider implementation.

## Automatic event copy

Event reconciliation prepares title and description proposals during issue
updates and active-event audits. It applies existing decisions before generation
so an authorized iteration request takes effect in the same run, then requests
review of newly generated drafts. The existing event lock covers all steps.
Readiness, source fingerprints, deduplication, approvals, and uncertain-request
recovery stay in their application and domain owners. The workflow only composes
these operations and forwards their independent failure evidence to reporting.
Cover and social generation remain explicit operations.

Decision history, 2026-10-30: preparation previously required a separate
workflow call, while routine reconciliation only reviewed stored proposals. A
consumer wired only to reconciliation consequently never received event copy.
Automatic text preparation replaces that split for title and description; both
reconciliation workflows now require explicit text AI configuration and the
content settings files. This trades additional required integration settings for
a complete preparation flow without a separate organizer trigger.

## Ownership and provider boundary

| Responsibility                                                            | Owner                                                          |
| ------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Event title and description rules and briefs                              | Event domain                                                   |
| Cover artwork rules and preferred output format                           | Publication domain                                             |
| Social post wording, destination, and reminder timing                     | Communication domain                                           |
| Generation calls, proposals, source fingerprints, review, and application | Journey application, through separate capability collaborators |
| Managed media identity, verification, and storage contract                | Publication                                                    |
| Vendor transport, request encoding, and response decoding                 | Generation adapter                                             |

Expose event copy, cover artwork, Slack post, and LinkedIn post generation as
separate operations. Organizer review is a separate operation. The
[workflow composition decision](0002-action-contracts.md#lifecycle-workflow-organization-2026-10-23)
groups these actions into preparation and promotion entry points while retaining
their responsibilities, per-target approvals and failure evidence. Shared durable
proposal mechanics do not own their business rules or become a general content
domain.

Journey owns provider-neutral `TextGeneration`, `ImageGeneration`, and
`GeneratedImage` contracts. They import no business domain types. Briefs contain
allowlisted public facts, instructions, and output requirements; they contain no
private contacts, event aggregates, proposals, review state, or persistence
services. The cover journey maps generated bytes into publication's media contract.

The Gemini implementation is `@meetup-automation/gemini-generation-gateway` under
`packages/adapter/generation/gemini-generation-gateway`. Its only workspace
dependency is journey. Separate text and image adapters share vendor transport
and codecs; runtime selects and injects the capabilities. The gateway validates
wire payloads and bounded responses, while business policies own editorial limits.

Image briefs supply preferred dimensions and media type. Provider code maps them
to supported aspect ratios and resolution tiers and rejects unsupported requests
before transport. Approximate provider settings do not establish exact output
dimensions; inspect the resulting bytes. Provider failures do not trigger an
automatic retry with uncertain side effects.

## Configuration when no content work exists (2026-10-29)

The standalone review action first checks the verified proposal store and authenticated
organizer submissions. When both are empty, content review completes without
loading content, event-publication, or social-publication configuration. Existing
proposals, including incomplete generation and past decisions, still require
configuration and normal review. Read or verification failures remain failures.
Generation and publication retain their required configuration. The 2026-10-30
automatic event-copy decision supersedes the ability to omit configuration from
the reconciliation workflows, while retaining this standalone review safeguard.

This replaces unconditional configuration loading during routine review, which
required placeholder files in consumers that use only event and asset workflows.
Journey owns the presence-of-work query through existing read ports; runtime
defers configuration and effect composition until that query finds work. GitHub
adapters retain state verification and submission authorization. Active content
review performs additional reads before its usual processing; it rereads state
and authority rather than treating the preliminary result as review approval.

## Accepted editorial formats

Use the resolved content language and validated public event facts. Preserve
technical names and authoritative talk identities and abstracts. Do not invent
logistics, affiliations, speaker credentials, urgency, or technical claims.
Placeholders must be resolved before approval.

### Event copy

The title is one plain-text thematic headline, at most 80 characters, combining
the shared technology or theme with a practical angle. Do not concatenate full
talk titles or add Markdown, dates, or the separately generated issue prefix.

The description uses short prose blocks separated by empty lines:

1. A brief meetup welcome with a leading emoji.
2. Date, start time, the host's public name, city, and shared theme.
3. A programme introduction, such as "Au programme :" in French.
4. In agenda order, one block per talk: relevant emoji, concise topic label,
   hyphen, public speaker names, and a short teaser grounded in the abstract.
5. A connecting sentence only when the talks share a meaningful theme.
6. An invitation to learn, discuss, and meet the community.

The description value is the prose, not the issue's display code fence. Apply the
12,000-character draft limit and validate the complete publication projection
against 49,000 characters, including appended authoritative talk details. Teasers
do not replace those details. Mention an apéritif or use a beer emoji only when
validated logistics confirm it; examples do not establish that fact for all events.

### Cover artwork

Generate four separate candidates, then review and approve one exact image.
Human-supplied covers can enter review directly. Each candidate has its own media
identity, fingerprint, and accessible description.

- Use bright, polished, humorous artwork inspired by Cloud Native, IT, open
  source, infrastructure, software engineering, and meetup community themes.
- Require the supplied event month and preserve its spelling, capitalization,
  language, and accents. The month is the only readable text, prominent and
  integrated into the scene. Do not add a year, product names, slogans, labels,
  commands, code, lettered logos, watermarks, or signatures.
- Represent the main technology, concept or practice of every supplied talk with
  a prominent recognizable motif. Use characteristic wordless symbols, actions
  and relationships; generic technology scenery alone is insufficient. Titles and
  abstracts are authoritative. The public event description can clarify subjects
  absent from them, including manual agendas. It is scoped to cover generation
  and source identity, without feeding event-copy outputs into their own inputs.
  A month alone remains enough when no validated agenda is available. Do not
  invent event logistics or additional subjects.
- Prefer landscape 1792×1024 PNG. Verify format and dimensions from bytes and show
  any deviation during review.
- Each canvas contains one coherent scene and artistic direction, filling the
  image without internal borders. Exclude grids, panels, collages, split screens,
  contact sheets, and composites cropped into candidates.
- Vary artistic technique, composition, metaphor, environment, and treatment of
  technology substantially across the four images; palette changes alone do not
  qualify.

Make four independent sequential requests. Each prompt describes only its own
scene, exact month, direction, and constraints, without earlier images, batch
indices, alternative styles, or conversation history. Store each request outcome
and inspect coherence, spelling, extra text, and metadata. Show successful images
separately and identify incomplete or nonconforming slots. Do not silently add
replacement requests or report a partial batch as four successful candidates.

### Social announcements

Support LinkedIn and a consumer-configured list of Slack channels. Generate Slack
proposals only for channels in that list, with no built-in community names or
fixed destination count. Slack channels share the same editorial structure, with
separate destination proposals. An empty list produces no Slack proposals.

Each post contains an opening, date and start time, host and city, a programme
list with one topic/speaker bullet and short teaser per talk, a grounded closing
invitation, and a verified registration link. Keep paragraphs short and separated
by empty lines, with talks in agenda order.

Slack uses colon emoji aliases and the canonical Meetup registration URL. It has
no required image, hashtags, or mention footer. LinkedIn uses Unicode emoji,
relevant hashtags, and a footer of verified public names; interactive profile
mentions remain an organizer task. A shortened registration URL is acceptable
only when its destination is verified.

LinkedIn attaches the generated announcement image. Its filename follows the
linked Drive template and publication's shared
[filename expression contract](0007-assets.md#filename-expressions). This
announcement asset is distinct from the cover illustration. Review the exact destination text
and attached bytes together; a Drive ID or current URL alone does not bind review
to immutable media content. Source or media changes require fresh approval.

### Pre-event reminders

Prepare one reminder per configured destination at D-7 and D0. The proposal count
follows the configured Slack channel list and LinkedIn destination. An approved
announcement does not approve its reminders. These public posts are separate from
internal organizer attention.

Record the event occurrence, destination, milestone, explicit planned local
publication time, and timezone. D0 must precede event start. The shorter body uses
a milestone opening, explicit event date and time, host and city, concise talk
highlights with public speaker names, and registration link. Retain each channel's
emoji style; LinkedIn also retains hashtags, verified mentions, and the reviewed
announcement image. Slack does not require those additions.

Use "Dans une semaine" for D-7 and "C'est aujourd'hui" for D0 in French, adapting
to the content language. Resolve relative wording against the planned publication
time. Recheck facts, status, timing, and approval; do not reuse stale countdowns.
Cancellation, postponement, or an already-started event makes pending reminders
ineligible. Date or time changes invalidate affected plans and require new review.

Generic "Announcement" and post-event "Social networks" checklist items remain
manual and unspecified. Obtain their destination and a format or example before
adding generation; their labels alone do not define a post. The supplied examples
do not establish platform limits or upload constraints; a dispatch integration
must verify and encode those requirements.

## Proposal lifecycle and approval

Generated and human-authored values enter the same versioned proposal lifecycle.
Bind decisions to the exact value revision, source facts, language, destination,
timing, and media fingerprints. Retain proposal history. A changed source or value
invalidates earlier approval. Importing a submission and approving it in the same
comment edit does not bypass review of the resulting proposal.

Verify the organizer's current authority, exact managed comment identity, and
decision provenance before applying content. Approval must be persisted before
its downstream effect. The general
[organizer approval safeguards](0003-organizer-approvals.md) still apply; granting review
authority does not authorize unrelated publication or delivery effects.

Reserve attempts durably before calling a provider. Reuse completed work on reruns
and retain uncertain attempts for explicit recovery rather than duplicating them.
An explicit new iteration creates one new text proposal or one tracked four-image
batch. Preserve the versioned proposal envelope, fingerprints, and reservation
identities across ownership refactors.

Apply approved event copy and managed media through their existing owners. Report
content through typed stage evidence, preserving state on incomplete evaluation.
This decision adds no social scheduling, dispatch, automatic checklist completion,
browser cover upload, or automatic announcement-image export. Those effects need
their own implemented contracts and authorization.
[ADR 0010](0010-social-publication.md) subsequently adds social dispatch, scheduling,
and delivery completion while preserving separate content and publication approval.

## Alternatives and consequences

Automatic publication would turn generation into authority. Review only after
applying content would not protect the previously published value. AI-only
authorship would exclude valid organizer submissions. One broad content component
or business-aware provider decoder would couple unrelated editorial policies and
make provider replacement affect domain behavior.

Business-owned briefs and neutral ports retain a reusable provider boundary.
Shared transport avoids duplicating vendor plumbing without merging text and
image responsibilities. Durable review and attempt state add storage and explicit
recovery, but preserve traceability and prevent approval or retries from silently
authorizing changed content.

## Decision history

On 2026-10-29, cover candidates moved to the dedicated `tmp-covers` child in the
[public asset layout](0007-assets.md#a-separate-pdf-snapshot). Moving an existing
candidate preserves its file identity and bytes but changes its source revision.
A fresh proposal and pending review are required; earlier approvals must not be
transferred. Candidates remain stored while reviews reference them.

On 2026-10-29, organizer review found the generated covers visually suitable but
too weakly connected to the talk subjects. This replaces optional topic
inspiration with explicit subject recognition in the scene. Manual talk titles
can omit the actual technology; cover facts now include the public description
as supplementary context. Stored proposals without this context retain their
source identities; adding or changing context creates a different cover source
and cannot reuse approval of an earlier image.

On 2026-10-29, live cover validation returned HTTP 400 for the image request.
The adapter forwarded the brief's preferred PNG MIME type, while the
[Interactions API reference](https://ai.google.dev/api/interactions-api)
lists only JPEG for image output. Provider mapping now requests JPEG,
retaining the preferred aspect ratio and resolution. This replaces direct MIME
forwarding without changing the domain's PNG/JPEG acceptance or the reviewed
artifact's actual encoding. A subsequent live request also rejected an explicit
image `delivery` setting, so the adapter uses the provider's default delivery.
The decoder still requires bounded inline image bytes. Failed generation
reservations remain in proposal history and require explicit recovery.

The same validation exposed a shared-drive verification gap: Drive does not
populate the file metadata's `permissions` field for shared-drive items. Content
media verification now reads the paginated permissions endpoint before accepting
public reader access. Incomplete or inaccessible listings cannot validate an
image. This does not grant sharing permissions or change folder access.

On 2026-10-27, the consumer-configured Slack channel list replaced the fixed
destination set in the social announcement and reminder decisions. Channel
identities and display names come from configuration; proposal counts follow
the configured destinations.
This refinement is accepted and implemented with the social publication work. The earlier decision
defined a fixed destination set and six reminder proposals. The
[social publication decision](0010-social-publication.md#ownership-and-destination-configuration)
applies the same channel list to dispatch, with no publication outside it.

On 2026-10-23, announcement filename validation was aligned with asset
reconciliation. The organizer's `YYYY-MM-DD - Annonce` example describes one <!-- codespell:ignore annonce -->
template, not a required global filename.
Publication owns the shared date-placeholder rule; the Drive adapter reads the
linked template and verifies its metadata. This replaces the fixed French label
without adding a second naming configuration.

The same-day [filename expression refinement](0007-assets.md#filename-expressions)
separates entity/property resolution from localized date formatting. The runtime
injects the same locale-aware renderer into reconciliation and announcement
validation; the Drive adapter does not interpret formatting patterns.
